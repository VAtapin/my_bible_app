# My Bible App — полный план продукта и разработки

## 1. Цель

Создать персональный клиент Bible Desktop, в котором человек получает не весь
набор возможностей платформы сразу, а собственное ежедневное приложение:
выбранные переводы Библии, молитвенное правило, календарь, чтения дня и другие
нужные ему разделы.

Приложение должно работать в трёх формах:

- PWA по персональной ссылке;
- приложение Android;
- приложение iOS.

Профиль и состав приложения едины для всех клиентов. Контент предоставляет
существующее API Bible Desktop.

## 2. Продуктовый результат

Пользователь должен суметь за одну-две минуты:

1. понять предложение продукта;
2. выбрать быстрый или ручной путь;
3. собрать минимальный полезный набор;
4. настроить только нужные уведомления;
5. подготовить материалы для офлайна;
6. открыть персональное приложение;
7. позднее изменить любой выбор.

Успех первого запуска определяется не количеством выбранных модулей, а тем,
что пользователь дошёл до готового приложения и открыл его повторно.

## 3. Что не является целью MVP

- перенос всех функций большого Bible Desktop;
- показ полного каталога на первом экране;
- отдельная сборка приложения для каждого пользователя;
- обязательная регистрация до знакомства с продуктом;
- полноценная социальная сеть;
- сложный редактор собственных богослужебных текстов;
- ИИ как обязательная часть ежедневного сценария;
- непрерывная фоновая работа вопреки ограничениям платформ;
- дублирование библейских и литургических данных в отдельном серверном проекте.

## 4. Пользовательские пути

### 4.1. Первый экран «Мой Bible Desktop»

Экран отвечает только на вопрос «Как вы хотите начать?» и содержит:

1. логотип и название Bible Desktop;
2. заголовок «Мой Bible Desktop»;
3. короткое обещание: «Соберите приложение под себя — только то, чем вы
   действительно пользуетесь»;
4. основное действие «Быстро настроить»;
5. вторичное действие «Настроить самому»;
6. отдельный путь «У меня уже есть приложение»;
7. спокойную подпись «Всё можно изменить позже».

На экране нет сетки всех модулей, длинного списка галочек и запроса системных
разрешений.

### 4.2. Быстрая настройка

Шаг 1. Выбор основы:

- «Каждый день»;
- «Чтение Библии»;
- «Молитва»;
- «Церковный календарь».

Шаг 2. Только релевантные уточнения:

- для Библии — конкретные переводы;
- для молитвы — утреннее правило, вечернее правило и молитвослов;
- для календаря — уровень событий;
- для чтения — при необходимости простой план чтения.

Шаг 3. Уведомления.

Шаг 4. Сводка и создание приложения.

Предустановки являются редактируемой начальной конфигурацией, а не отдельными
режимами продукта.

### 4.3. Ручная настройка

Вместо общего списка показываются тематические разделы:

1. Библия;
2. Ежедневная молитва;
3. Церковный календарь;
4. Чтение и изучение;
5. Дополнительно.

После открытия темы пользователь видит только относящиеся к ней варианты.
Выбранные элементы постоянно представлены в компактном блоке «Ваше приложение».
Порядок разделов можно изменить после выбора, но перетаскивание не является
единственным способом управления.

### 4.4. Восстановление существующего приложения

Нужно предусмотреть три механизма, вводимые поэтапно:

- открытие персональной ссылки;
- короткий код восстановления;
- привязка к аккаунту или e-mail по желанию пользователя.

Персональная ссылка не должна содержать последовательный или угадываемый ID.
Секрет восстановления нельзя хранить в открытом виде на сервере.

### 4.5. Повторное использование

После создания стартовым становится экран «Сегодня», составленный из выбранных
элементов. В настройках всегда доступно действие «Настроить моё приложение».

Пример состава экрана «Сегодня»:

- продолжить чтение;
- чтения и событие дня;
- ближайшее молитвенное правило;
- избранное;
- состояние офлайн-данных, только если требуется действие.

## 5. Состав MVP

### 5.1. Библия

- выбор одного или нескольких опубликованных переводов;
- отдельный выбор основного перевода;
- каталог книг и глав;
- сохранение последнего места;
- закладки;
- базовый поиск при наличии сети;
- офлайн-доступ к загруженным переводам;
- понятное указание объёма загрузки.

Параллельный перевод допустим в MVP, если существующий API и производительность
локальной базы позволяют реализовать его без задержки основного выпуска.

### 5.2. Молитвы

- утреннее правило;
- вечернее правило;
- каталог опубликованных молитв;
- избранные молитвы;
- сохранение позиции чтения;
- офлайн-доступ.

### 5.3. Календарь

- день церковного календаря;
- двунадесятые и другие выбранные праздники;
- пост;
- чтения дня;
- переход к библейскому тексту выбранного перевода;
- локальный календарный горизонт для офлайн-работы;
- обновление данных при появлении сети.

### 5.4. Богослужебные тексты

Кандидаты на первый выпуск:

- Часослов;
- Псалтирь;
- акафисты.

Для каждого раздела до включения в MVP проверяются:

- опубликованность и полнота корпуса;
- стабильность API;
- лицензирование и атрибуция;
- размер офлайн-пакета;
- корректная работа разных редакций и языков.

### 5.5. Настройки

- состав приложения;
- порядок разделов;
- основной перевод;
- язык интерфейса;
- размер текста и тема;
- уведомления;
- управление офлайн-данными;
- восстановление и перенос профиля;
- удаление профиля и локальных данных.

## 6. Уведомления

### 6.1. Категории

- утреннее правило;
- вечернее правило;
- чтение дня;
- напоминание о плане чтения;
- только двунадесятые праздники;
- большие праздники и посты;
- расширенный церковный календарь;
- личные напоминания — после MVP.

### 6.2. Правила опыта пользователя

- системное разрешение запрашивается только после выбора конкретного типа;
- пользователь выбирает время и дни;
- выключенное состояние является полноценным выбором;
- нет повторных сообщений с формулировками вины или давления;
- каждую категорию можно отключить независимо;
- приложение объясняет, почему уведомление могло не прийти;
- настройки учитывают часовой пояс и его изменение.

### 6.3. Техническая модель

- предсказуемые ежедневные и календарные события планируются локально;
- локальное расписание создаётся скользящим окном и регулярно пополняется;
- push используется для обновлений контента и событий, которые нельзя было
  вычислить заранее;
- получение контента не должно зависеть от гарантированного фонового запуска;
- сервер хранит только необходимые push-токены и пользовательские подписки;
- отказ в системном разрешении не блокирует остальные функции.

## 7. Offline-first

### 7.1. Что доступно без сети

- оболочка приложения и навигация;
- конфигурация пользователя;
- загруженные переводы Библии;
- выбранные молитвы и богослужебные тексты;
- календарь и чтения в пределах загруженного горизонта;
- закладки, заметки и история чтения;
- локально запланированные уведомления.

Сетевые функции явно обозначаются, но их отсутствие не ломает чтение.

### 7.2. Пакеты контента

Сервер должен отдавать манифест с:

- типом и идентификатором пакета;
- версией схемы;
- версией содержимого;
- размером;
- контрольной суммой;
- зависимостями;
- временем публикации.

Клиент сначала скачивает новый пакет, проверяет его и только затем атомарно
переключается на новую версию. Прерванная загрузка не должна портить уже
работающие данные.

### 7.3. Локальное хранение

- мобильные приложения: SQLite и файловое хранилище;
- PWA: IndexedDB и Cache Storage;
- пользовательские изменения пишутся локально немедленно;
- очередь синхронизации повторяет операции после восстановления сети;
- миграции локальной схемы версионируются и тестируются;
- пользователь видит размер каждого загруженного раздела;
- очистка контента отделена от удаления закладок и профиля.

### 7.4. Конфликты синхронизации

Для простых настроек применяется последняя подтверждённая версия с серверным
номером ревизии. Для заметок нельзя молча перезаписывать два разных изменения:
конфликтующие версии сохраняются до разрешения пользователем.

## 8. Профиль и серверная конфигурация

Минимальная концептуальная структура:

```json
{
  "schemaVersion": 1,
  "profileId": "opaque-random-id",
  "revision": 1,
  "modules": ["bible", "prayers", "calendar"],
  "bible": {
    "primaryTranslation": "translation-code",
    "translations": ["translation-code"]
  },
  "prayers": {
    "collections": ["morning", "evening"]
  },
  "calendar": {
    "notificationLevel": "twelve-great-feasts"
  },
  "layout": ["today", "bible", "prayers", "calendar"]
}
```

Реальные коды переводов и произведений всегда получаются из API. Клиент не
угадывает их по языку или названию.

Серверная модель должна поддерживать:

- случайный публичный идентификатор;
- отдельный секрет изменения или восстановления;
- версию схемы и ревизию;
- оптимистическую блокировку при записи;
- отметки создания, последней активности и удаления;
- необязательную привязку к пользователю;
- экспорт и удаление данных.

Автоматическое удаление неактивных конфигураций не включать без отдельной
политики, предупреждения и способа восстановления. Малый размер JSON сам по себе
не является причиной удалять профиль через шесть месяцев.

## 9. Архитектура клиентов

### 9.1. Рекомендуемое направление

Одна кодовая база Vue 3 + TypeScript + Capacitor:

- веб-сборка работает как PWA;
- Capacitor создаёт Android и iOS проекты;
- UI и продуктовая логика общие;
- SQLite, уведомления, push, файловое хранилище и системные ссылки реализуются
  через адаптеры платформ;
- бизнес-логика не импортирует плагины Capacitor напрямую.

### 9.2. Слои

```text
UI и пользовательские сценарии
        ↓
Прикладные сервисы
        ↓
Доменные модели и правила
        ↓
Порты хранения / уведомлений / сети
        ↓
PWA-, Android- и iOS-адаптеры
```

Такое разделение позволяет тестировать сценарии без устройства и не связывает
всё приложение с конкретным плагином.

### 9.3. API

Типизированный клиент должен:

- иметь единый базовый URL по окружению;
- проверять форму критичных ответов;
- поддерживать отмену запросов и тайм-ауты;
- различать offline, timeout, 4xx и 5xx;
- повторять только безопасные операции;
- передавать версию приложения и поддерживаемую схему;
- не содержать секретов Bible Desktop в клиентской сборке.

Запросы к защищённым внешним сервисам, включая календарь, идут через сервер
Bible Desktop. Ключи внешних API в приложение не встраиваются.

## 10. Изменения в основном API

До реализации нужно провести отдельный контрактный аудит. Предполагаемые новые
возможности, если их нет:

- CRUD персонального профиля;
- восстановление и ротация секрета;
- синхронизация пользовательских изменений по ревизиям;
- регистрация push-токенов и подписок;
- манифесты и пакетная загрузка офлайн-контента;
- endpoint проверки доступных обновлений;
- удаление/экспорт профиля.

Обычный контент продолжает использовать существующие маршруты переводов,
молитв, календаря и богослужебной библиотеки. Новый серверный API реализуется в
`D:\Projekte\BibleDesktop`, а не внутри мобильного клиента.

## 11. Безопасность и приватность

- персональные URL имеют достаточную случайность и не перебираются;
- ссылка просмотра и право изменения разделяются, если продукт допускает шаринг;
- секреты хранятся на сервере в виде хешей, где это применимо;
- трафик только по HTTPS;
- push-токены можно отозвать;
- логи не содержат тексты личных заметок, секретные ссылки и токены;
- данные устройства защищаются возможностями платформы;
- аналитика не собирает содержание молитв, заметок и чтения;
- пользователь может экспортировать и удалить свои данные;
- для аккаунта, синхронизации и аналитики готовится прозрачная политика
  конфиденциальности.

## 12. Доступность и дизайн

- минимальная поддерживаемая ширина — 320 px;
- все основные действия доступны касанием и клавиатурой;
- зона касания около 44 × 44 px;
- порядок нельзя менять только перетаскиванием;
- поддерживаются системный размер шрифта и масштабирование;
- светлая и тёмная темы имеют достаточный контраст;
- иконки сопровождаются текстом или доступным названием;
- важное состояние не передаётся только цветом;
- церковнославянский текст получает корректный Unicode-шрифт и язык;
- формулировки уведомлений спокойные, без давления.

## 13. Аналитика продукта

Собирать только агрегированные события, необходимые для улучшения пути:

- открытие конструктора;
- выбор быстрого или ручного режима;
- завершение каждого шага;
- создание профиля;
- завершение офлайн-загрузки;
- повторное открытие приложения;
- ошибка загрузки или восстановления.

Не отправлять выбранные молитвы, содержание заметок, поисковые запросы и тексты
чтения без отдельного обоснования и явного согласия.

## 14. Тестирование

### 14.1. Автоматические проверки

- модульные тесты доменных правил и пресетов;
- контрактные тесты API-клиента;
- тесты миграций локальной базы;
- тесты очереди синхронизации и конфликтов;
- тесты расчёта расписания уведомлений;
- компонентные тесты конструктора;
- сквозные PWA-тесты;
- smoke-сборки Android и iOS.

### 14.2. Проверки на устройствах

- первый запуск без сети и с медленной сетью;
- прерывание загрузки офлайн-пакета;
- нехватка места;
- запрет уведомлений;
- смена часового пояса;
- перезапуск и обновление приложения;
- восстановление по ссылке и коду;
- крупный системный шрифт;
- старое устройство в минимально поддерживаемой версии ОС;
- переход из уведомления к правильному экрану.

## 15. Этапы разработки

### Этап 0. Контракты и технический прототип

Результаты:

- инвентаризация готовых API;
- минимальный Vue/Capacitor-каркас;
- одна тестовая глава в SQLite/IndexedDB;
- работа без сети после перезапуска;
- одно локальное уведомление на iOS и Android;
- тестовая PWA-установка;
- проверка сборок на реальных устройствах;
- решение о библиотеке SQLite и стратегии Service Worker.

Критерий выхода: критические возможности работают без неподтверждённых
предположений о плагинах и платформах.

### Этап 1. Конструктор и локальный профиль

- первый экран;
- быстрый и ручной пути;
- модель конфигурации;
- локальное сохранение;
- экран сводки;
- «Настроить моё приложение»;
- тесты основных ветвей.

### Этап 2. Библия и базовый офлайн

- интеграция переводов, книг и глав;
- чтение;
- загрузка перевода;
- версия и обновление пакета;
- последнее место и закладки;
- экран управления хранилищем.

### Этап 3. Молитвы и календарь

- молитвослов и правила;
- календарь и чтения дня;
- переход к библейскому тексту;
- офлайн-горизонт календаря;
- проверка часовых поясов и дат.

### Этап 4. Уведомления

- категории и время;
- контекстный запрос разрешений;
- локальное скользящее расписание;
- переход из уведомления;
- push-инфраструктура для обновлений;
- диагностика состояния разрешений.

### Этап 5. Серверный профиль и восстановление

- безопасная персональная ссылка;
- код восстановления;
- синхронизация конфигурации;
- очередь локальных изменений;
- удаление и экспорт;
- необязательная привязка к аккаунту.

### Этап 6. Подготовка к магазинам

- иконки, splash screen и store metadata;
- privacy policy и disclosures;
- accessibility review;
- тестирование обновления и миграций;
- TestFlight и закрытое тестирование Google Play;
- инструкции для App Review;
- мониторинг ошибок без чувствительных данных.

### Этап 7. Пилот и выпуск

- небольшой пилот с реальными пользователями;
- проверка процента завершения конструктора;
- анализ проблем офлайн-загрузки и уведомлений;
- исправления критических сценариев;
- поэтапный production rollout;
- plan rollback для клиента и серверных контрактов.

## 16. Приоритеты

### P0 — обязательное

- короткий первый запуск;
- выбор конкретного перевода;
- Библия, молитвы и календарь;
- работа без сети;
- управляемые уведомления;
- безопасный профиль;
- восстановление;
- изменение конфигурации.

### P1 — после устойчивого MVP

- Псалтирь, Часослов и акафисты;
- параллельные переводы;
- планы чтения;
- синхронизация заметок;
- аудио;
- системные виджеты;
- семейные или приходские подборки.

### P2 — отдельные продуктовые задачи

- ИИ-помощник;
- сложные персональные рекомендации;
- социальные функции;
- публичный каталог пользовательских наборов;
- Apple Watch, Wear OS и автомобильные сценарии.

## 17. Риски

| Риск | Снижение риска |
| --- | --- |
| Конструктор снова становится длинным каталогом | Ограничить первый экран выбором пути, использовать темы и пресеты |
| Нативное приложение выглядит как WebView | Реальный офлайн, нативные уведомления, хранение и системная интеграция |
| Фоновое обновление не запускается вовремя | Локальное расписание, запасной офлайн-горизонт, обновление при открытии |
| Большие переводы занимают много места | Размер до загрузки, пакеты, выборочное удаление, атомарные обновления |
| Потеря персональной ссылки | Код восстановления и необязательная привязка к аккаунту |
| API меняется и ломает офлайн | Версии схем, контрактные тесты и совместимые изменения |
| Несогласованные данные календаря | Bible Desktop остаётся единым серверным посредником |
| Пользователь отвергает уведомления | Запрос только после конкретного выбора и объяснения пользы |
| MVP разрастается | P0/P1/P2 и отдельные критерии выхода каждого этапа |

## 18. Критерии готовности MVP

MVP готов к пилоту, когда:

- новый пользователь завершает настройку без инструкции;
- быстрый путь занимает не более нескольких коротких решений;
- выбранные материалы открываются после отключения сети и перезапуска;
- повреждённая или прерванная загрузка не ломает старую версию;
- локальные уведомления работают на тестовых iOS и Android устройствах;
- отказ от уведомлений не ухудшает чтение;
- профиль восстанавливается подтверждённым способом;
- пользователь может изменить состав и удалить данные;
- ключевые сценарии покрыты автоматическими тестами;
- подготовлены политика конфиденциальности и материалы магазинов;
- API и клиент имеют совместимую версию контракта.

## 19. Следующее практическое действие

Начать не с полного UI, а с этапа 0: создать минимальный технический каркас и
доказать на реальных устройствах четыре критические вещи — API, локальную базу,
офлайн-перезапуск и локальные уведомления. После этого зафиксировать стек и
реализовать первый экран конструктора как первый законченный продуктовый блок.
